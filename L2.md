### chalanges (Could you please share the real chalanges and  Tell me about a time you took ownership of a difficult problem. )

> I’d like to share a real challenge I faced while working on a Micro Frontend architecture at Citi.

**The main challenge was how to share common external dependencies across multiple Micro Frontends without creating version-compatibility or security issues.**

> To give you some background, initially, each Micro Frontend was using its own dependencies, and the application was working as expected. However, this approach introduced several challenges.

> First, the overall **bundle size was increasing** because the same dependencies could be loaded multiple times. Second, there was a possibility of **version compatibility issues** between different Micro Frontends. If the versions were not compatible, it could potentially lead to application failures and impact the overall stability of the application.

> The biggest challenge was that development was already completed and each Micro Frontend was working independently with its own dependencies. However, the **Citi Security and Vulnerability teams had not provided the required approval** for the architecture because of these concerns.

> So, instead of immediately making an architectural change, I first researched different **dependency-sharing and version-management approaches**, while keeping security, compatibility, and compliance requirements in mind.

> After my analysis, I proposed a solution and demonstrated it to the **Core Federation team**, as well as the **Security and Vulnerability teams**. We discussed the approach, addressed their concerns, and thoroughly tested the solution.

> Eventually, the solution was approved by all the teams and successfully deployed to production.

> **This experience taught me that in a Micro Frontend architecture, independent development and deployment are important, but dependency management, version compatibility, security, and maintainability are equally critical.**



###  What would be your approach if you encounter a production issue?

If I encounter a production issue, my first approach will be to understand the impact, then analyze the logs and monitoring data to identify the root cause. I would stabilize the system with a rollback or workaround if required, keep the stakeholders informed, implement and test the permanent fix, and make sure the issue doesn’t happen again.


### Have you handled any production issues?

Yes, I have handled production issues. Let me share a recent incident.

Recently, I developed a feature where customers could submit a request to close their account. During production testing, I noticed that **three closure Order IDs were being generated for a single customer request**, which made it difficult to track the request from the customer’s perspective.

I started the analysis by checking the UI and backend flow. I found that there was **no duplicate API call from the UI**. The issue was actually in the backend, where a retry mechanism was triggering the request again without properly waiting for the **Kafka acknowledgment**.

I immediately informed the relevant stakeholders, explained the impact, and got approval for the production fix. I then coordinated with the teams involved in the development, implemented the fix, tested it, and supported the **patch deployment**.

After the fix, we validated the flow to ensure that a single customer request generated only one Order ID.




### How do you identify the root cause?

I normally start by understanding the symptoms and reproducing the issue if possible.

Then I trace the complete flow, including the UI, APIs, backend services, messaging systems, logs, and recent deployments. I also check whether there were any configuration or infrastructure changes.

For example, in my recent incident, I confirmed that the UI was not making duplicate calls and then traced the issue to the backend retry mechanism and Kafka acknowledgment handling.

### What is your approach to RCA?

My RCA approach is to identify not only what failed, but also why it failed.

I analyze the timeline, logs, code changes, dependencies, and system behavior to identify the root cause. After fixing the issue, I document the RCA, define corrective and preventive actions, and add appropriate test cases or monitoring to prevent recurrence.

### How do you communicate during a production incident?

During a production incident, I keep communication clear, concise, and proactive.

First, I communicate the impact and severity to the relevant stakeholders. Then I provide regular updates about the investigation, current status, workaround or mitigation, and expected next steps.

Once the issue is resolved, I communicate the final resolution and RCA.


### When would you rollback a deployment?

I would consider a rollback when a recent deployment is clearly causing a critical production issue and the impact cannot be safely mitigated quickly.

My priority would be to restore the stable version and minimize customer impact. After stabilization, I would investigate the root cause, fix the issue, test it properly, and then redeploy through the normal process.

### How do you prevent the same production issue from happening again?

After resolving a production issue, I focus on identifying the root cause and the preventive actions.

Depending on the issue, I would add appropriate unit or integration test cases, improve error handling and monitoring, review the retry or failure-handling mechanism, and update the documentation.

For the Order ID issue, for example, I would ensure the retry mechanism properly handles Kafka acknowledgment and add test cases for duplicate-request scenarios.

### How do you prioritize multiple production issues?

I prioritize production issues based on **customer impact, business impact, severity, and urgency**.

For example, an issue affecting a large number of customers or a critical banking transaction would take priority over a low-impact issue.

I would also communicate the prioritization to stakeholders and make sure each issue has an owner and clear next steps.

### How do you handle pressure from business stakeholders during an incident?

During a production incident, I try to stay calm and focus on facts and resolution rather than pressure.

I clearly communicate what we know, what we are investigating, the current impact, and the next steps. I also provide regular updates instead of waiting until the issue is completely resolved.

My focus is to minimize customer impact, restore the service safely, and then provide a clear RCA and preventive actions.



### ** AI / Modern Engineering **###


### 1. How are you using AI in your day-to-day development?

I use AI tools like **GitHub Copilot, ChatGPT, and Devin** as part of my day-to-day development. I use them for tasks such as generating boilerplate code, understanding existing code, writing unit tests, debugging, refactoring, and exploring different implementation approaches.

For example, with Angular or Node.js, I can use AI to quickly generate a starting point or analyze an issue. I then review, test, and modify the output based on our application requirements and coding standards.

### 2. How do you use GitHub Copilot/ChatGPT?

I use **GitHub Copilot** mainly during coding for code completion, boilerplate generation, refactoring, and generating unit-test scenarios.

I use **ChatGPT** more for problem-solving, explaining unfamiliar code, comparing approaches, debugging, and creating or improving technical solutions.

For example, if I have an RxJS or Angular problem, I can ask ChatGPT to explain different approaches and their trade-offs, then I choose and implement the approach that fits our application.

### 3. Have you used AI for debugging?

Yes. I use AI as an additional debugging assistant. I provide the relevant error message, code flow, logs, or a simplified version of the problem and ask AI to identify possible root causes.

For example, if an Angular application has an unexpected API call or a Node.js service has an error, I can use AI to analyze the code flow and suggest possible causes.

However, I don't blindly accept the suggestion. I verify it using **logs, debugging tools, tests, and the actual application behavior** before making any change.

### 4. How do you ensure AI-generated code is secure and correct?

I treat AI-generated code as a suggestion, not as production-ready code.

First, I review the code against our **requirements, coding standards, security guidelines, and architecture**. Then I run unit tests, integration tests, static analysis such as **SonarQube**, and security checks such as **Snyk** where applicable.

For sensitive areas like authentication, authorization, data handling, or banking-related functionality, I give additional manual review and validation.

Ultimately, the developer remains responsible for the code that goes into production.

### 5. How can AI improve developer productivity?

AI can improve productivity by reducing repetitive work and helping developers get to a solution faster.

For example, it can help with **boilerplate code, unit tests, documentation, code explanations, debugging, refactoring, and exploring implementation options**.

This allows developers to spend more time on higher-value activities such as **architecture, business logic, performance, security, and design decisions**.

I see AI as a productivity accelerator rather than a replacement for engineering judgment.

### 6. What are the risks of using AI in software development?

There are several risks. AI-generated code can contain **security vulnerabilities, incorrect logic, outdated information, or performance issues**. There can also be concerns around **sensitive data and confidential source code** being shared with AI tools.

There is also a risk of developers becoming overly dependent on AI without understanding the generated code.

So I believe we need proper **data-handling guidelines, code review, security scanning, testing, and human validation** before AI-generated code reaches production.

### One strong line to remember

> **“I use AI to accelerate development, but I don't outsource engineering judgment to AI. I remain responsible for understanding, validating, testing, securing, and maintaining the code.”**
